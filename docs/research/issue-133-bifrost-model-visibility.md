# Research: Issue #133 — Bifrost UI model visibility (only Cloudflare shows)

**Date:** 2026-09-06  
**Scope:** `src/llm_discovery/bifrost/generator.py`, `scripts/generate-bifrost-config.py`, `src/llm_discovery/bifrost/shim.py`, `data/bifrost/config.json`, `data/bifrost/shim_map.json`, `data/bifrost/config.db`, `data/results/*.yaml`, `src/llm_discovery/config.py`, Bifrost runtime (:8080)
**Related:** #132 (wayfinder map)

## Executive summary

**Symptom (reported):** Bifrost UI provider pane lists all providers, but model pane lists only Cloudflare models.

**Reproduced today (2026-09-06):**

- **Generator is healthy.** With full env, `data/bifrost/config.json` emits **20 providers**, `shim_map.json` has `flash=95` / `max=217` / `contributor_free=2` (314 keeps). Both files are internally consistent and match `data/results/*.yaml` keep totals. This is **not** a generator filtering bug.
- **Live Bifrost diverges:**
  - `/api/providers` -> 16 providers active (agnes, ainative, bazaarlink, cloudflare, google, kilo_ai, llm7, modelscope, nararouter, navy_ai, nvidia_nim, ollama_cloud, opencode_zen, reka, requesty, zai) — missing 4 that are in `config.json`: cerebras, groq, mistral, openrouter.
  - `/api/models?limit=1000` -> `total=304` with correct per-provider distribution (e.g. requesty:158, ainative:31, ... cloudflare:8). Catalog present via management API.
  - `/v1/models` (OpenAI-compatible, what chat completions and many UIs use) -> `{"error":"no valid keys found for provider: <X>"}` for every provider including Cloudflare when the Bifrost process lacks env secrets.
- **Root cause hypothesis (most likely): (b) Bifrost runtime health / key-resolution filtering plus (d) stale config.db.** Bifrost stores keys as `env.VAR` refs. At request time it resolves them against the container process environment. In this host the container has zero `*_API_KEY` vars (fallback file absent, Podman secret unavailable — see below). Bifrost therefore marks every key invalid and `/v1/models` health-filters to zero, while `/api/providers` still lists providers as active/unknown (catalog, not health). Historically, if only Cloudflare vars were injected, only the 8 @cf/* models would survive the health filter — matching the reported symptom exactly. Compounding: `config.db` (96 s newer than `config.json` today) contains only 16 providers, so even after fixing secrets a restart/re-ingest is required.

**Not the root cause:** generator strict flags, shim_map contract, or deduplication. Those are working as specified; the shipped artifacts prove it.

### 2. Hypothesis drill-down (a)-(e)

#### (a) Generator filtering — NOT the fault (ruled out)

Tested: strict_contributor_free, missing env, Cloudflare dual-var gate, catalog omission, allowlist dedup.

- **strict_contributor_free (`generator.py:20-21`, `81-107`):** filters only `contributor_free` tier to entries where `model_id` contains "contributor" (case-insensitive). Current shim_map 2-entry contributor pool correctly passes the filter; no zero-price broadening leak. Covered by `tests/test_bifrost_generator.py:38-45`, `216-230`.
- **Missing env gate (`generator.py:164-179`):** skips a provider if its secret Var is absent from `available_env`, plus the Cloudflare dual-var gate (`generator.py:165-170` requires both CLOUDFLARE_API_KEY and CLOUDFLARE_ACCOUNT_ID). Reproduction with `available_env=set()` yields providers emitted: [], tier_counts all 0, empty_tiers=[flash,max,contributor_free] — an obvious empty-tier failure that `scripts/generate-bifrost-config.py --check` would exit non-zero for (`generate-bifrost-config.py:91-97`). With full env the generator emits the full 20-provider catalog and empty_tiers=[]. The shipped config.json matches the full-env result, so generation was performed with keys present. Not the current file-level bug.
- **Catalog omission (`generator.py:219-223`):** keeps for providers absent from `config/providers.yaml` are appended to skipped. No silent drop of keep-all variants: `generator.py:141-154` populates shim_map with all tier variants, provider_to_models keeps duplicates across providers, and `190-197` dedups only within a provider while preserving order (tested in `tests/test_bifrost_generator.py:232-244`).

Verdict on (a): generator logic is correct and the emitted artifacts prove it.

#### (b) Bifrost runtime health / key-resolution filtering — PRIMARY HYPOTHESIS

**How Bifrost resolves keys:** `config.json` stores `"value": "env.XXX"` (never inline secrets; `generator.py:203`). At runtime Bifrost (Go gateway, via Podman Quadlet `~/.config/containers/systemd/bifrost.container`) resolves env.* against the container process environment, supplied via either default Secret=bifrost-env,type=env (Podman secret) or fallback EnvironmentFile=%h/.config/bifrost/bifrost.env when scripts/setup.sh --secrets=file is used.

Why only Cloudflare historically: Bifrost health-filters /v1/models to only providers with at least one valid (resolvable) key. If at the time of the report the container environment contained only CLOUDFLARE_API_KEY + CLOUDFLARE_ACCOUNT_ID, the gateway would still list all providers in /api/providers (catalog, not health-filtered) but /v1/models would route-filter to the single healthy provider — users see "all providers present" but "only @cf/* models". The alternative UI path (data/bifrost/shim_map.json + shim.py:pick_model_for_tier) is independent and would also 503 if the file-level shim_map were empty; today it is not empty, so the shim would route correctly — confirming the bug is not in the shim but in the Bifrost gateway layer the UI queries.

Cited lines:

- src/llm_discovery/bifrost/generator.py:164-179 — per-provider env gate + Cloudflare dual-var gate.
- src/llm_discovery/bifrost/generator.py:199-206 — "value": f"env.{secret}" (deferred resolution).
- data/bifrost/config.json — shows env.VAR refs, not inline secrets.
- Podman unit: .config/containers/systemd/bifrost.container:8-22 (Secret=bifrost-env, PublishPort=8080:8080, Volume=.../data/bifrost:/app/data:Z).

#### (c) Bifrost UI endpoint contract vs shim_map — mismatch, not a bug

The UI has two plausible model sources:

| Source | What it lists | Health-filtered? | Current value |
|---|---|---|---|
| GET /api/models (Bifrost management API) | All allowlisted models per provider, from config.json | No | 304 (stale DB) / 314 (file truth) |
| GET /v1/models (OpenAI-compatible, health-checks keys) | Only models whose provider has >=1 resolvable key | Yes | 0 today (all keys unresolvable) |
| data/bifrost/shim_map.json + shim.py:pick_model_for_tier | Tier pools (flash/max/contributor_free) used by project shim | No (file-only) | 95/217/2 |

If the UI is wired to /v1/models (expected for an OpenAI-compatible gateway), the "only Cloudflare" symptom is precisely the health-filtered view under partial secrets.

#### (d) Stale config.db not regenerated — CONFIRMED secondary fault

```text

config.db    mtime 2026-09-06 16:59:38  (+96 s, WAL active at capture)
```

Yet DB contents lag file contents:

- File: 20 providers. DB: 16 providers; missing cerebras, groq, mistral, openrouter.
- DB config_models is empty (SELECT count(*) FROM config_models -> 0); live model population is driven by the config_keys allowlist, but the stale DB means even /api/models undercounts (304 vs file-truth 314) and a fresh generate-bifrost-config.py + restart will be required.
- Bifrost /api/config reports "restart_required":{"required":false}, which is misleading — the hash comparison is on the DB view; the file-vs-DB provider count divergence is authoritative evidence of staleness.

#### (e) Provider allowlist dedup within vs keep-all across — correct

- generator.py:141-154 — provider_to_models and shim_map are populated by iterating grouped tiers in order, so within-provider allowlist order reflects tier priority.
- generator.py:190-197 — dedup is within a provider only (seen set per provider), preserving order; duplicates across providers are intentionally kept (keep-all), giving duplicates natural weight in shim.py:32 uniform pick.
- No evidence of cross-provider dedup collapsing models into Cloudflare.

## Root cause hypothesis (ranked)

### Hypothesis 1 (most likely): Missing container secrets -> Bifrost health-filters /v1/models to Cloudflare only

Confidence: High. Evidence chain: Secret=bifrost-env unavailable (read-only /run/user/1000/libpod), fallback ~/.config/bifrost/bifrost.env absent, host env has 0 API keys, Bifrost /api/keys shows unresolved env.* refs, and /v1/models returns no valid keys found uniformly. Historic partial injection (only Cloudflare pair present) reproduces the reported "only @cf/*" symptom directly. Generator and file artifacts are healthy, isolating the fault to the runtime boundary.

### Hypothesis 2: Stale config.db (missing 4 providers, config_models=0)

Confidence: Confirmed as a secondary fault. Explains the 304 vs 314 count mismatch and why even with secrets restored the UI would still be incomplete until Bifrost re-ingests config.json.

### Hypothesis 3: Generator strict flags or catalog omission — Ruled out

Confidence: Ruled out by file-level evidence (full 20-provider emit, tier counts match keep totals, contributor filter correct, no silent drops).

### Hypothesis 4: UI endpoint contract confusion — Contributing factor

Confidence: Contributing factor for symptom visibility, but not a bug to fix by switching endpoints — fix secrets so /v1/models is healthy.

## Fix sketch

### Immediate (operator)

1. Restore secrets (one of):

   ```bash
   # Preferred: re-create Podman secret
   infisical export --projectId "$LLM_SHARED_PROJECT_ID" --env dev \
     --format dotenv > /tmp/bifrost.env
   podman secret rm bifrost-env 2>/dev/null || true
   podman secret create --env-file /tmp/bifrost.env bifrost-env
   shred -u /tmp/bifrost.env || rm /tmp/bifrost.env

   # Fallback if Podman secret remains broken (HV FS read-only):
   mkdir -p ~/.config/bifrost
   infisical export --projectId "$LLM_SHARED_PROJECT_ID" --env dev \
     --format dotenv > ~/.config/bifrost/bifrost.env

   # Then: scripts/setup.sh --yes --secrets=file
   ```

   ```bash
   grep -E "CLOUDFLARE_API_KEY|CLOUDFLARE_ACCOUNT_ID|OPENROUTER_API_KEY|CEREBRAS_API_KEY" ~/.config/bifrost/bifrost.env | sed 's/=.*/=***/'
   ```

### Code change (recommended, prevents recurrence)

No bug in generator.py or shim.py logic, but add a guard + observability so the "only Cloudflare" symptom surfaces at generation time instead of at UI time.

**A. Fail-loud on partial secrets at generation time (scripts/generate-bifrost-config.py):**

```python
# sketch
parser.add_argument("--strict", action="store_true",
    help="fail if any provider with keeps is skipped due to missing env")
...
if result["skipped"] and args.strict:
    keeps_providers = {k["provider"] for k in keeps}
    missing_key_providers = [p for p in result["skipped"] if p in keeps_providers]
    if missing_key_providers:
        print(f"--strict: missing env for keep-having providers: {', '.join(missing_key_providers)}", file=sys.stderr)
        return 2
if result["empty_tiers"]:
    return 1
```

Wire CI to run `uv run python scripts/generate-bifrost-config.py --check --strict` on PRs that touch `data/results/*.yaml` or `config/providers.yaml`.

**B. Surface live DB-vs-file drift (observability):**

Add a lightweight drift check to `scripts/generate-bifrost-config.py --check` that compares `config.json` provider set vs live `/api/providers` when Bifrost is reachable.

**C. Optional: make Cloudflare gate non-silent**

In `generator.py:165-170` enrich skipped reporting to name which var is missing.
